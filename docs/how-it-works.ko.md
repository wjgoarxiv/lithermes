# 작동 방식, 단계별로

[← README로 돌아가기](../README_Ko-KR.md#작동-방식) · [English](./how-it-works.md)

README는 경로를 상자 그림과 공정 플랜트, 두 장의 그림으로 보여 줍니다. 이 페이지는 두 그림을 상자 하나, 스트림 하나씩 따라갑니다.

## 경로

LitHermes는 Python 플러그인입니다. Hermes가 플러그인을 불러오면 `register(ctx)`가 훅, 명령, 스킬, 작업 도구를 등록하고, 훅은 모델이나 도구를 호출하기 직전과 직후에 끼어듭니다. 상자 그림은 요청 하나를 입력한 순간부터 따라갑니다.

1. `lit`으로 시작하는 프롬프트도, `/lit-plan` 같은 슬래시 명령도 같은 곳에 도착하고, 거기서 `pre_llm_call` 훅이나 등록된 명령이 경로를 고릅니다. 그냥 `lit`이면 `litwork`, 계획이면 `lit-plan` 하는 식입니다.
2. 스킬은 `goal_*` 도구로 목표를 다루고, 스킬이 실행한 터미널 명령은 하나하나 `post_tool_call` 훅이 기록하고 서명합니다. 작업 검토에서는 `delegate_task` 검토자 다섯이 변경을 각자 따로 읽습니다.
3. 답변이 나가기 직전에는 `pre_verify`와 `transform_llm_output`이 게이트를 확인합니다. 게이트가 열려 있으면 "다 됐다"가 그대로 남고, 닫혀 있으면 답변 끝에 `⛔ LIT: not done`과 그 이유가 붙습니다.
4. 그림 오른쪽은 모두 프로젝트 안의 파일입니다. 점선은 새 턴이 일의 진행 상황을 아는 이유를 보여 줍니다. 모델을 부를 때마다 목표 기록을 다시 읽기 때문입니다.

## 공정 플랜트

같은 경로를 작은 공정 플랜트로 그려 보면, 상자 그림에서는 잘 보이지 않던 것이 드러납니다. 일은 한 바퀴 돌고 다시 돕니다. 번호 붙은 줄이 무엇을 싣고 어느 훅이나 도구를 거치는지는 그림 속 스트림 표에 있습니다.

- **들어오기.** 요청은 왼쪽으로 들어옵니다. 그냥 `lit`은 곧장 작업 유닛으로 가고, `lit plan`은 계획 유닛에 먼저 들릅니다.
- **검토와 게이트.** 끝난 작업은 단이 다섯 개인 검토 칼럼을 지나는데, 이 다섯 단이 검토자 다섯입니다. 그 뒤에는 삼방 밸브에 달린 분석계처럼 게이트가 서 있습니다.
- **다시 한 바퀴.** 통과한 답변은 완료로 나가고, 통과하지 못한 답변은 `LIT: not done`이 되어 작업 유닛으로 돌아갑니다. 게이트가 열릴 때까지 이 순환이 이어집니다.
- **기록.** 실행 기록과 검토 영수증은 기록 탱크, 곧 프로젝트의 `.hermes/lithermes/`로 모입니다. 탱크는 턴마다 목표 요약을 라우터로 돌려보내고, 핸드오프 카드는 다음 세션으로 넘깁니다.

## 모델이 보는 것

다음 모델 호출 전에는 context 훅이 이 기록을 읽어, 지금 목표가 무엇이고 어디까지 왔는지 모델에게 건넵니다. `lit`으로 시작하는 평범한 프롬프트는 플러그인이 경로를 정하고, 슬래시 명령은 바로 해당 스킬로 가며, 붙여 넣은 코드나 복사한 명령은 자료로만 읽고 지시로 따르지 않습니다. 모델은 여전히 Hermes Agent가 돌리고, 권한 확인, 로그인, 모델 접근, 실제 화면이 필요한 검사도 모두 Hermes 쪽에서 처리합니다.
