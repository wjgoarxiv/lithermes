# Privacy and local records

LitHermes runs inside your Hermes Agent environment. Its local records are separate from the prompts and tool activity that Hermes may send to your configured model providers, gateways or external services. This document describes the installer and plugin source; it does not promise that a complete Hermes session is offline or covered by one telemetry policy.

## Network activity

Fetching a package through npm contacts the configured registry and follows npm's own configuration and caching behavior. The installer update code can query `registry.npmjs.org` for package version metadata. Eligible interactive install/check/doctor commands and the supported first-turn update path can initiate an automatic update; update transactions can invoke a package installer and record backup/journal/doctor results locally.

`LITHERMES_NO_UPDATE_CHECK=1` or `NO_UPDATE_NOTIFIER=1` disables the installer's update checks and automatic-update gate. `LITHERMES_NO_AUTO_UPDATE=1` disables automatic installation. The relevant CLI gates also suppress updates for `--offline`, `--json`, `--dry-run`, CI and noninteractive streams. These controls do not make an outer `npm exec` fetch offline, and do not disable Hermes model calls or network-capable tools. Use an already available local CLI for a local `doctor --offline` check.

See [updateNotifier.js](../packages/lithermes-installer/src/lib/updateNotifier.js) for exact eligibility, registry request and transaction behavior. Workflows that fetch sources or use browser/tools follow the permissions and services selected for that task.

Automatic handoff is off by default and makes no network call. When you switch it on, the plugin keeps the latest context reading of each session in memory and saves only your switch and last percent in Hermes home `lithermes/auto-handoff.json` (mode 0600, never written through a symlink). The model writes the handoff to `HANDOFF.md` or `.handoff/HANDOFF.md` in your project, which can hold local session detail, so keep it out of public commits. After a compaction the plugin reads that file, only when it is a regular file that carries this session's id and was written after the request, and adds at most 1,400 bytes of it, redacted, to the next turn, which goes to your configured model provider like any other turn. See [auto_handoff.py](../packages/lithermes-installer/assets/lithermes-plugin/auto_handoff.py).

## Files and retention

| Location | What it can contain |
|---|---|
| Hermes home `plugins/lithermes/` | Installed Python plugin and skill payload |
| Hermes home `config.yaml` | Plugin enablement and managed model/display settings alongside existing host settings |
| Hermes home `lithermes/` | Install manifest, event log, update cache, transaction receipts and backups; your automatic-handoff switch in `auto-handoff.json`; `litgoal.key`, the random key that seals your goal files |
| Hermes home `lithermes/retained-python-cache-*/` | Relocated Python cache bytes and a `retention.json` inventory |
| Workspace `.hermes/lithermes/` | Run state, ledgers, goal/evidence records, signed run notes (`runs.jsonl`: a command hash, a redacted preview of at most 100 characters, the exit code), the saved gate verdict (`gate.json`), the test baseline (`testguard.json`), handoff cards (`handoff/`) and knowledge claims |
| Workspace `plans/` and task-selected output paths | Plans and artifacts created by the requested workflow |

The installer resolves the home from `--hermes-home`, then `HERMES_HOME`, then `~/.hermes`. See [installation](../packages/lithermes-installer/src/lib/install.js), [runtime paths and event writes](../packages/lithermes-installer/assets/lithermes-plugin/core_runtime.py), and [run records](../packages/lithermes-installer/assets/lithermes-plugin/core_runs.py).

Skill-review state created by earlier versions is inert in the current release. The installer and plugin do not read, rewrite, migrate, or delete those files; their owner may remove them separately.

On a default repeat installation, eligible interpreter-tagged caches associated with unchanged owned Python sources are moved outside the plugin payload into a unique `retained-python-cache-*` backup. These are preserved bytes, not redacted event records: they may contain source constants or paths and should not be attached to reports without review. `retention.json` includes the original plugin path, relative cache paths, hashes and observed directory identities. The installer does not execute, trust or reuse retained bytecode under new source. Successful output reports the backup path, and that install's manifest records `retainedPythonCache`.

Cache backups have no automatic expiry, cleanup or restoration. They survive later installs and uninstall, and can remain after a partial failure; a later manifest need not retain older backup references. The local profile owner decides when to archive or delete them. They are separate from automatic-update snapshots in `lithermes/auto-update/<transaction-id>/backup/`, which may retain plugin files, configuration and other transaction targets. Preserve needed recovery evidence before cleanup. See [migration](./migration.md) for the cache eligibility, destructive `--force` exception and unsafe-path rollback behavior.

Redaction runs on several task/event persistence paths, but pattern-based redaction cannot guarantee removal of every sensitive value. Review diagnostics, plans, artifacts and handoffs before sharing. Local storage does not mean that every stored value stays out of model context: workflow context and accepted knowledge can be included in a Hermes request.

Wikify captures structured events as `review-needed`; accepted records may enter context. Set `LITHERMES_WIKIFY_CAPTURE=0`, or use `hermes lithermes knowledge capture off` in the relevant workspace to stop capture. The opt-out does not erase existing claims or stop other run/event records. [knowledge.py](../packages/lithermes-installer/assets/lithermes-plugin/knowledge.py) defines claims and settings under `.hermes/lithermes/knowledge/`.

Uninstall removes matching managed plugin files and disables the plugin. It does not implement a comprehensive personal-data erasure process: run records, event logs, retained Python caches, update backups, modified files and host settings can remain. Stop active Hermes sessions, review the paths you own, and back up needed work before manually deleting retained records. Follow [migration and removal](./migration.md) for ownership details. Keep secrets and local records out of Git commits and issue attachments.

## What the plugin checks, reads and starts

Four parts of LitHermes depend on what happened on your machine, so this section says how each one works and where it stops. The plugin ships a longer technical version in its [plugin README](../packages/lithermes-installer/assets/lithermes-plugin/README.md).

**Evidence the plugin saw itself.** Hermes tells the plugin each time a terminal command finishes. The plugin writes a note of it to the session's `runs.jsonl` (a hash of the command, a redacted preview of at most 100 characters, the exit code, the time and a fingerprint of the project files) and signs the note with a key that it makes when it starts and keeps only in memory. A goal's "tests pass" evidence counts only when it points at one of those notes with exit code 0. A command that Hermes only started in the background is not noted, because the host reports exit code 0 the moment it spawns one. If a project file changes after the run, that evidence goes stale and the gate asks for a new run. To tell, the plugin asks `git` only for file names and object ids and hashes the files itself, so no program from the project's git settings runs. When a reply says "done" while the gate is still closed, the plugin adds a line that starts with `⛔ LIT: not done` and names the reason; the same text hidden in a comment or code block does not stop it, and a goal marked complete by hand in its file does not count as finished. The same line, saying that no goal was opened, is added when a `lit` work session says "done" and never opened a goal. In the same case of an open gate, the plugin also answers Hermes' `pre_verify` hook after code edits, which asks the agent to run one more turn with the gate's reasons; Hermes limits how often that can repeat. The signature shows that this Hermes process saw the command finish with that exit code and that nobody edited the note afterwards. It does not show that the command tested anything useful or that the code is right. The key is gone when the gateway restarts, so runs from before the restart have to be run again.

**A watch on your tests.** When a goal starts, LitHermes counts the tests, assertions and skip markers in each Python and JavaScript test file. If a later edit removes tests or assertions, adds a skip or deletes a file, the gate closes with a blocker that the model cannot clear. A test file that is replaced by a symlink, grows past 1 MiB or cannot be scanned within five seconds counts as weakened too. You clear a blocker by typing `/lit-accept-tests <reason>` for the current session (or `/lit-accept-tests --all-sessions <reason>` for every session of the project), and the reason goes into the goal's ledger. The counts sit in `testguard.json` inside the project, so a model with a raw shell could empty that file and silence the watch. The count is a line pattern, so a rewrite that keeps the counts passes it. Treat the watch as a tripwire for ordinary slips.

**Picking up where you left off.** In a new session, LitHermes looks through the other sessions' goals in the same project, and only goals this installation saved count: each goal file carries a seal made with a random key in `litgoal.key` in your Hermes home, so a goal file that arrives with a cloned repository, or that was edited by hand, is ignored. If one is unfinished, the first reply mentions it once, and nothing is adopted until you type `lit` or `lit resume`. So it reads other sessions' goal files in your project, and the goal's title and its count of open criteria go to your model provider with that turn. Adoption copies the goal, ledger, evidence files and test baseline into the new session; run notes are not copied. `LITHERMES_GOAL_RESUME=0` turns the offer off. When a session that held a goal is closed, LitHermes writes a handoff card to `.hermes/lithermes/handoff/` (`<session>.json`, `latest.json` and `latest.md`), built from files on disk with no model call. Hermes decides when a session is closed. For `hermes -z` and Desktop chat the gateway closes it after a grace period once nothing is attached, so the card can appear well after your last message, and a gateway restart before that loses it.

**A pane in Hermes Desktop.** A right-hand pane and a status-bar chip show the goal, whether its gate is open and a six-step timeline. They poll one read-only route that the plugin adds to the Hermes gateway, `GET /api/plugins/lithermes/goal?cwd=<project>`. The route reads state files in the project folder you pass, and that folder has to resolve to a place inside your home directory, otherwise it answers HTTP 400. What it returns is redacted and length-capped. The plugin sets no CORS headers, adds no authentication of its own and opens no port; who can reach the route is whatever Hermes allows for plugin routes. The route cannot re-verify a signed run note, so the gate it shows is labelled as reported by the session. It also lists up to eight recent signed runs with their command preview, exit code, time and the names of files changed since, with your home folder shown as `~` and the plugin folder as `<lithermes>`; `gate.json` keeps that time and up to eight changed file names for each cited run. When the gate changes in a local session, the plugin posts one message per goal through Hermes' `ctx.post_message` (Desktop shows it as a toast; the pane raises none of its own). It carries the goal title and the gate's first reason and stays on your machine unless Hermes forwards the session elsewhere. Desktop 0.23 keeps the pane off until you turn it on under Capabilities > Plugins, and it copies the pane into an app-level folder that every profile shares.

**Processes it starts.** The plugin runs `git`, `node` (for the film and Office helpers), a Python prose detector, `pdftotext` and a browser version probe. It builds every argument list itself and never uses a shell; the one caller-supplied value is the base ref of a review diff, which goes after `--`. Each call has a time limit. Each gets only a short list of environment variables: the search path, home folder, user, locale, temporary folder, shell, terminal type, Hermes home and the XDG base folders (plus the system variables Windows needs). Provider keys and tokens in your environment are not passed down. Scripts that the model runs through Hermes' own terminal tool go through Hermes' approval flow and are outside this list.

**What it reads from Hermes.** To tell which project a gateway session belongs to, the plugin asks the host's own working-folder helpers (`agent.runtime_cwd`, `tools.terminal_tool`), because the shared gateway process runs in the Hermes home. It reads them from the modules Hermes has already loaded and never imports them, and it never uses as a project the Hermes home, anything inside it or inside `~/.hermes`, or your home folder itself. The automatic handoff feature reads Hermes' compaction defaults, the model's context window and the name of the compact command (`agent.context_compressor`, `hermes_cli.config_defaults`, `agent.model_metadata`, `hermes_cli.commands`), and `doctor` reads the Hermes version from `hermes_cli`. Hermes publishes no plugin interface for these. Each lookup is read-only and wrapped, so when Hermes moves one of them the comparison goes missing and nothing else breaks. `hermes plugins validate` lists these imports as a caution under the catalog's public-surfaces rule.

**Scan note.** The `sudo_usage` report that the same scan used to raise came from the design database of `frontend-ui-ux`. That database moved to `wjgoarxiv-skills` with the skill, so the LitHermes payload no longer carries it.

**Hermes version.** `plugin.yaml` declares `requires_hermes: ">=0.21.3"`, the oldest Hermes whose Desktop plugin surfaces and plugin hooks this version uses. A Hermes older than that skips the plugin with a version message.
