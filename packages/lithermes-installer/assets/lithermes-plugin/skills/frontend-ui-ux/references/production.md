# From request to working surface

Use the selected frontend-ui-ux skill to interpret the request, not to expand it. An explicit build request authorizes the named interface change; critique or planning stays read-only. A UI mentioned as context is not a redesign request. Natural-route context helps choose behavior but grants no file or host permission.

## Bound the work

Before editing, identify the target route/component, repository and permitted paths, stack, user task, existing brand, behaviors and states to preserve, and requested outcome. Keep the direction note concise. Use the evidence-capable v1beta2 Design Contract as an evolving inventory; do not block a bounded build on completing JSON first or add a routine approval gate.

There is no mandatory interview. Ask only when two plausible answers materially change scope, architecture, permissions, accessibility, or visual direction. Ask one high-impact question at a time, retain earlier answers across rounds, and do not re-ask a resolved question. Continue for as many rounds as materially necessary; when the brief is bounded, state the default and proceed. Review, plan, and keyword-only requests remain read-only.

If a brief lists competing visual directions, treat them as undecided or unchosen. "acceptable" is not a choice or a delegation. Ask about the open direction in a separate round; do not declare a default or start building. Only when the brief gives no visual direction may the reversible authored default apply without asking.

## Direction defaults and preservation

Use existing brand and system values where present. When no brand, direction, or subject-implied medium is supplied, start from default-editorial-pixel.json and create an original, task-specific pixel illustration as the primary visual anchor: crisp integer-grid edges, each cell at least 6 CSS px, nearest-neighbor scaling. A generic gradient or rounded symbol is not a substitute. Keep the illustration decorative when live text conveys the task; otherwise provide meaningful alternative text. Never borrow a reference site's artwork, proprietary font, or copy.

Choose a visual medium that fits the subject and audience before applying a house default. Use imagery only with appropriate use rights, and never imply that illustrative stock material documents a real subject. For a fictional concept, provide complete, coherent sample content and label it as such in accompanying documentation; for real entities, use supplied or verified facts and never present invented details as verified facts. Remove authoring notes and unfinished prompts from the delivered interface. Keep consistent naming and visual identity across the page. Check text against its background at desktop and phone widths for legibility and overlap.

Fit actual Korean and Latin strings before choosing line breaks. Narrow screens should restructure the layout rather than shrink a desktop composition. Preserve semantic elements, keyboard order, visible focus, validation recovery, and programmatic labels. Ensure a hidden attribute still wins over a component display utility (for example, .empty[hidden] { display: none; }). Give animated accents a useful static state.

## Build and inspect

Use the declared stack and request scope. Exercise the main action in a real browser at 320, 390, and 1440 CSS px when those dimensions suit the surface; inspect focus, validation/error recovery, success, and overflow. Capture the exact built revision. Preserve prior failure captures. If a native capture path is unavailable, name the gap; any authorized external replay must be labeled separately. A clean validator does not prove visual quality.

Keep capture manifests and review labels in internal project evidence, not as UI copy. Finish with the working files or preview and only the material unresolved boundary.
